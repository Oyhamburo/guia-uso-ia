Nivel 2 · anatomía de un sistema de IA

De tu mensaje a una acción real.

No todo es “la IA”. Cada capa cumple un trabajo distinto: una recibe tu pedido, otra coordina, el modelo razona y las herramientas actúan.

1 · Dónde empieza tu pedido
DCliente desktop

Una aplicación instalada. Puede integrar archivos, sistema operativo y atajos propios.

WCliente web

Corre en el navegador. Es simple de abrir, pero opera dentro de los permisos del sitio.

>_Terminal

Interfaz de texto directa. Ideal para agentes que trabajan con código, comandos y automatizaciones.

↓
2 · Quién ejecuta el sistema
LocalTu computadora

Una app desktop o un proceso de terminal ejecuta el agente y el harness. Desde ahí se llama al modelo remoto o local.

Servicio webEl backend del producto

En una plataforma gestionada, el proveedor ejecuta el harness en sus servidores y te muestra el resultado en el navegador.

No lo ejecutaEl modelo

El modelo sólo recibe contexto y devuelve texto o una propuesta de tool call. No inicia el harness, ni abre archivos, ni ejecuta herramientas.

Aunque se lo pidas en el prompt: el modelo no obtiene permisos nuevos. Puede solicitar una acción, pero el software que lo rodea decide si existe esa tool y si está permitido ejecutarla.
↓
3 · El agente
AAgente · decide qué hacer después

Tiene un objetivo y mantiene un ciclo: consulta al modelo, elige una tool, observa el resultado y decide el próximo paso. Puede usar muchas tools durante una tarea.

AgenteTool
¿Tiene un objetivo?Sí. Intenta completar una tarea.No. Sólo recibe una operación.
¿Decide el siguiente paso?Sí, dentro de sus permisos.No. Devuelve un resultado y termina.
¿Mantiene un ciclo?Sí: pensar → actuar → observar → continuar.No: entrada → ejecución → salida.
Ejemplo“Revisá el repositorio y corregí el error”.read_file(path) o run_tests().
Prueba rápida: si puede preguntarse “¿qué hago ahora?” y continuar con otra acción, es comportamiento de agente. Si solamente ejecuta una llamada y devuelve datos, es una tool.

4 · El harness
Harness · el entorno que permite y controla al agenteCarga contexto y skills, expone tools, aplica permisos y conserva el estado del ciclo.
Amplía capacidad

Skill: “así se hace”

Es conocimiento procedural reutilizable. Le enseña al agente un método, orden o criterio especializado para resolver una clase de tareas.

Pregunta
¿Cómo conviene realizar este trabajo?
Activación
Cuando la tarea coincide con su tema.
Efecto
Agrega pasos, técnicas y conocimiento.
Ejemplos
Revisar un PR, crear infraestructura AWS, diseñar un diagrama.
Skill de despliegue: ejecutar tests → construir artefacto → revisar cambios → desplegar → comprobar salud.
Reduce libertad

Guardrail: “esto no puede pasar”

Es una restricción o control. Define límites sobre datos, herramientas, resultados o acciones, incluso si el modelo propone ignorarlos.

Pregunta
¿Qué está permitido y bajo qué condiciones?
Activación
Siempre o dentro de un alcance definido.
Efecto
Bloquea, filtra, valida o pide aprobación.
Ejemplos
No revelar secretos, no borrar datos, no publicar sin confirmación.
Guardrail de despliegue: producción requiere aprobación humana; una credencial nunca puede imprimirse en logs.

Entonces, ¿cómo sabe el modelo cuál es cuál?

1 · RegistrarEl producto o harness descubre archivos, configuración o componentes registrados.
2 · ClasificarLa metadata indica cuándo usar una skill y qué políticas o permisos son obligatorios.
3 · PrepararEl harness arma el contexto: objetivo, skill elegida, reglas, herramientas y datos relevantes.
4 · ControlarEl modelo propone una acción; el runtime la permite, la rechaza o solicita aprobación.
¿Están en carpetas distintas? Pueden estarlo porque ayuda a organizarlos, pero la carpeta no crea la diferencia. La diferencia real está en cómo el harness los registra, qué prioridad les asigna y si el límite se aplica sólo como texto o también mediante código.
Guardrail blandoEs una instrucción dentro del contexto: “no hagas X”. Depende de que el modelo la siga correctamente.
Guardrail duroEs una restricción del runtime: permiso denegado, sandbox, esquema obligatorio o aprobación humana. Aunque el modelo pida hacer X, el sistema no lo ejecuta.

¿Dónde viven el harness, las skills y las reglas?

No tienen una ubicación universal. El harness busca en varios niveles y combina lo que encuentra.

5 · Tres piezas diferentes
Pensar Modelo

Genera la próxima respuesta o propuesta. Recibe contexto; no ejecuta directamente acciones sobre tu sistema.

Agente→API o runtime local→Modelo
Ejecutar Tool · hace una sola cosa

No mantiene por sí misma el objetivo ni el ciclo de decisión de la tarea. Recibe parámetros, ejecuta una operación y devuelve un resultado. El agente decide cuándo llamarla y qué hacer con la respuesta.

Agente decide→Tool ejecuta→Resultado→Agente continúa
Ejemplos: read_file, run_tests, web_search. Ninguna decide por sí sola cuál usar después.
Conectar MCP

No es una tool: es un protocolo. Un servidor MCP puede publicar varias tools, recursos y prompts para que distintos clientes los descubran de forma estándar.

Agente→Cliente MCP→Servidor MCP→Tools
La diferencia esencial: el agente tiene un objetivo y decide; la tool sólo ejecuta una operación. El harness controla el ciclo, el modelo ayuda a elegir y MCP puede conectar las tools.

6 · Contexto

La mesa de trabajo temporal del modelo

El contexto es todo lo que el modelo puede ver en una petición: instrucciones, conversación, skills cargadas, fragmentos de archivos y resultados de tools. No es lo mismo que entrenamiento ni memoria permanente.

Sesión

Es el período de trabajo que mantiene la aplicación: conversación, estado, archivos y acciones acumuladas.

→
Petición al modelo

Cada vez que enviás un mensaje o el agente necesita decidir, el harness prepara una nueva llamada.

→
Contexto de esa petición

Es la selección concreta de información que el modelo recibe en esa llamada.

Una sesión puede tener muchas peticiones. El modelo no mantiene abierta la sesión por sí mismo: la aplicación conserva el historial y reconstruye el contexto para cada llamada. Si algo no se vuelve a enviar, el modelo no puede verlo.
¿Qué es un token? Es una unidad en la que el modelo divide texto y código: puede ser una palabra corta, parte de una palabra, un signo o varios caracteres. Por eso 1.000.000 de tokens no equivale exactamente a 1.000.000 de palabras.

“Lost in the middle”

En contextos largos, distintos modelos mostraron una tendencia: recuperan mejor información ubicada al principio o al final y pueden fallar más cuando el dato importante queda enterrado en el medio.

  • Colocá reglas críticas al comienzo.
  • Repetí la pregunta o el resultado esperado al final.
  • Estructurá el material largo con títulos y bloques claros.

Es una tendencia medida, no una ley universal. Los modelos y técnicas de recuperación siguen mejorando.

Cuando no entra más: compactación

Al acercarse al límite, un harness puede resumir mensajes antiguos, descartar resultados repetidos y conservar instrucciones o hechos considerados importantes.

Contexto llenoConversación, archivos y resultados acumulados.
→
CompactarSeleccionar, resumir y eliminar redundancia.
→
Contexto nuevoResumen + mensajes recientes + datos esenciales.
El costo: compactar ahorra espacio, pero puede perder matices, decisiones pequeñas o relaciones causales. El modelo continúa desde el resumen; no conserva mágicamente todo el texto original.
